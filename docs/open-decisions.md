# Provider 決策與明確延後事項

本文件區分真實運行前需要選擇的 provider，與使用者已明確延後、因此不構成本批缺口的工作。

## 本批前置的最少 provider 決策

- **直播平台**：選擇聊天室事件輸入與文字輸出平台，並確認所需授權、身份、速率限制及錯誤策略。尚未接線或建立憑證。
- **正式模型**：選擇模型 provider、部署位置及成本／逾時限制。現有 model client 是 fixture。
- **天氣**：若要回覆即時天氣，再選擇資料 provider、地區覆蓋與刷新規則；目前是虛構 fixture。
- **人物／遊戲材料**：來源方向已決定為自有知識格式，以及人工整理的 Wiki／網路材料；本機 prebuild 接收已整理的 JSON bundle。若要啟用網路抓取或自動研究，才需確定允許端點、授權／引用方式、更新頻率與 provider。現行 query 仍讀本機 fixture，沒有網路來源接線。

完成這些選擇前，不建立外部憑證、持久權限或真實服務連線。以上決策只在啟用相應真實 provider 前需要，不阻塞現有本機功能。

## 其他仍待決策的運行政策

- **預建審核政策**：是否所有 prebuild candidate 都必須人工審核；本機流程保守地要求人工核准。
- **缺口研究角色**：由誰整理來源及審核衝突、過期材料；缺口補充已要求人工審核後才能發布。
- **SOP 處理方式**：invalid、未觸發、loop guard、限流及部分失敗的人工處理時限與角色。
- **隱私與保留**：conversation snapshot 範圍、聊天原文及研究材料保存期限、刪除和使用者識別政策。
- **輸出失敗**：送出結果不確定時維持 `delivery_state=unknown`；人工處理或重送策略尚未指定。
- **審核身份**：本機 reviewer 是文字欄位；正式多人使用時的身分驗證與簽核責任尚未決定。

## 明確延後（非本批缺口）

- **跨 repo 交換／整合**：沒有共用 package、DB、RPC、跨 repo import、runtime 整合或自動 gap export/import 的本批要求。缺口包與知識 bundle 的跨 repo 交換格式、匯入流程和相容政策不在本批；只在使用者另行排入時重新評估。
- **STT 與逐字稿 query**：主播逐字稿來源、保存、查詢、喚醒詞與保留政策整組保留為未來方向，本批不實作，也不作為目前功能驗收條件。一般逐字稿不觸發回覆。

## 本機狀態界線

聊天輸入驗證、SOP、snapshot、規則型用途拆分、五用途 fixture query、Prompt、事件與執行記錄，以及獨立知識準備 workflow 都在各自 repo 本機驗證。天氣／人物／遊戲素材、模型和平台輸出仍是 fixture 或 stub。這些本機結果不宣稱真實 provider 已連接。
